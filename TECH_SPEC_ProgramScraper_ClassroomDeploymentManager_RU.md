# Техническое задание и пошаговый план разработки
## Объединение ProgramScraper и ClassroomSoftwareDeploy в Classroom Deployment Manager

**Версия документа:** 1.0  
**Дата:** 23.11.2026  
**Назначение:** инструкция для ИИ-агента-разработчика, который будет выполнять интеграцию небольшими проверяемыми коммитами.

---

# 0. Инструкция агенту: как работать с этим заданием

Ты работаешь над существующими проектами. Твоя задача — **не переписать их с нуля**, а постепенно объединить, сохранив работоспособность исходных инструментов.

Обязательные правила:

1. Перед изменениями изучи оба исходных проекта и зафиксируй их фактическое состояние. Не считай это ТЗ заменой просмотра кода.
2. Работай по одному пункту плана за раз. Один коммит — одно логически завершённое изменение.
3. После каждого коммита запускай подходящие тесты и проверку синтаксиса PowerShell. Не переходи к следующему пункту при сломанных тестах.
4. Не делай массовый рефакторинг и не меняй одновременно формат данных, интерфейс и алгоритм установки.
5. Не удаляй и не переименовывай существующие скрипты без необходимости. Если нужна миграция, оставь совместимый wrapper и опиши переход.
6. Не добавляй в проект реальные установщики, большие бинарные файлы, лицензированные дистрибутивы или секреты. В Git хранятся код, схемы, конфигурационные примеры и тестовые фикстуры.
7. Не запускай массовое скачивание, установку ПО, удалённые команды, изменение реестра или перезагрузку без явного разрешения пользователя. В разработке используй mock/dry-run и тестовые файлы.
8. Не угадывай тихие ключи EXE-инсталляторов. Параметры установки должны быть проверены для конкретного продукта и версии. Не устанавливай приложение, если параметры неизвестны.
9. Не обходи лицензионные механизмы и авторизацию Adobe, Autodesk, Chaos, Maxon, Microsoft и других поставщиков. Для таких продуктов предусмотрен ручной/официальный workflow.
10. Клиентские компьютеры не имеют доступа к интернету. **Любая установка на целевом ПК должна выполняться только из заранее подготовленных локальных файлов** — с USB/SSD или из локальной сети.
11. Сохраняй совместимость с Windows PowerShell 5.1, пока не будет отдельного решения о повышении минимальной версии. Избегай синтаксиса и API, доступных только в PowerShell 7.
12. Не добавляй обязательные сторонние PowerShell-модули в runtime. Dev-зависимости (например, Pester) допустимы и должны быть явно описаны.
13. Не считай наличие пакета Chocolatey/WinGet достаточным для автономной установки. В комплект должны попасть реальные payload-файлы, зависимости и компоненты, необходимые установщику.
14. После каждого коммита сообщай: SHA/номер коммита, что изменено, какие тесты выполнены, что осталось, есть ли известные ограничения.

**Правило остановки:** если обнаружено расхождение между кодом и этим ТЗ, сначала зафиксируй его в отчёте и предложи минимальный безопасный путь. Не исправляй большой набор несвязанных проблем одним коммитом.

# 1. Цель проекта

Создать единую Windows-систему **Classroom Deployment Manager (CDM)** для подготовки каталога ПО, создания автономных пакетов приложений, развёртывания этих пакетов на 20–30 компьютерах компьютерного класса и проверки результата.

Ключевой исходный смысл ProgramScraper: собрать список реально установленных приложений на одном или нескольких компьютерах, чтобы на его основе сформировать список программ, которые нужно подготовить к скачиванию. Пост-развёртывательная проверка — полезная дополнительная функция, но не должна вытеснять эту первоначальную задачу.

## 1.1. Главный пользовательский сценарий

1. Пользователь сканирует один или несколько действующих компьютеров с помощью ProgramScraper.
2. Система собирает сведения об установленных приложениях и объединяет результаты в общий каталог-кандидат.
3. Пользователь просматривает каталог, исключает лишнее и подтверждает программы, которые нужно подготовить.
4. Для каждой подтверждённой программы система предлагает источник и способ получения установщика: прямой официальный URL, пакетный репозиторий/адаптер, либо ручная загрузка с официальной страницы.
5. На компьютере с интернетом пользователь создаёт пакет выпуска. В пакет попадают реальные установщики, обязательные зависимости, манифест, контрольные суммы и сведения об источниках.
6. Пакет используется двумя способами:
   - **USB/SSD:** подключить носитель к целевому ПК без интернета и запустить локальную установку;
   - **LAN:** скопировать пакет с подготовительного/серверного компьютера по локальной сети на целевые ПК и установить его локально.
7. После развёртывания система по запросу запускает повторную инвентаризацию и сравнивает фактическое состояние с планом.

## 1.2. Обязательные ограничения

- Целевые ПК работают без доступа к интернету.
- Интернет разрешён только на подготовительном компьютере, где создаётся пакет.
- Приложения устанавливаются из локального payload, а не скачиваются на целевом ПК.
- Браузеры Chrome, Firefox, Edge и Яндекс Браузер являются обычными desktop-программами и могут входить в каталог. Исключаются именно веб-сервисы/сайты, которые не устанавливаются на Windows.
- Система должна быть пригодна для класса примерно из 20–30 компьютеров.
- Не предполагать, что всё ПО бесплатное. В каталоге хранить тип лицензии и пользовательскую отметку о наличии права на установку.
- Не выполнять автоматическую установку программы, если нет проверенного локального установщика, команды установки и правил определения результата.

# 2. Исходные проекты и проверенное состояние

## 2.1. ProgramScraper

Репозиторий: <https://github.com/circumF1ex/programscraper>

В текущем репозитории на ветке `main` присутствуют `.gitattributes`, `.gitignore`, `Get-InstalledPrograms.ps1`, `README.md` и `Run.bat`. README описывает сбор сведений о Windows 10/11 в `.xlsx` с отдельными листами. Текущий скрипт — большой PowerShell-файл (примерно 933 строки / 39,7 KB по отображению GitHub на дату проверки).

README описывает следующие листы отчёта:

- `Сводка` — ПК/ОС, права, источники данных и количество записей;
- `Программы пользователя` — uninstall-записи текущего и других пользовательских профилей;
- `Программы системы x64`;
- `Программы системы x86`;
- `Windows и компоненты`;
- `Обновления KB`;
- `Автозагрузка`;
- `winget` (если доступен);
- `Драйверы`.

Скрипт использует реестр HKLM x64/x86, загруженные пользовательские кусты HKEY_USERS и NTUSER.DAT профилей, а также WMI/QFE, Win32_PnPSignedDriver, Run-ключи/Startup и опционально `winget list`. Для выгрузки XLSX сторонняя библиотека/Excel не требуется: используется Open XML + ZIP средствами .NET. Есть параметры `-OutputDir`, `-SkipWinget`, `-SkipAutostart`. При чтении NTUSER.DAT предусмотрены загрузка/выгрузка временных кустов и очистка оставшихся PSRep_*.

**Требование:** сохранить текущий XLSX-отчёт и существующий способ запуска `Run.bat`. Новые форматы и интеграционные функции добавлять рядом, не ломая существующий сценарий.

## 2.2. ClassroomSoftwareDeploy — текущий офлайн-архив

Базовый архив, переданный пользователем: `ClassroomSoftwareDeploy-OfflineUSB.zip`.

Внутри проверены следующие файлы:

```text
ClassroomSoftwareDeploy/
├── Config/
│   ├── MANUAL-DOWNLOADS.csv
│   ├── PREDEPLOY-CHECKLIST.txt
│   ├── apps.json
│   ├── computers.txt
│   ├── requirements.txt
│   └── software-catalog.csv
├── Logs/
├── Packages/
├── Scripts/
│   ├── Install-Local.ps1
│   ├── Install-PythonLibraries.ps1
│   ├── Install-USB.cmd
│   ├── Invoke-NetworkDeploy.ps1
│   ├── Prepare-OfflineMedia.cmd
│   └── Prepare-OfflineMedia.ps1
├── INSTALL-FROM-USB.cmd
├── PREPARE-USB.cmd
└── README.md
```

Текущие функции:

- `Prepare-OfflineMedia.ps1` скачивает файлы по `DownloadUrl` в `Packages/<Id>/`, вычисляет SHA-256, формирует `OFFLINE-DOWNLOAD-RESULTS.csv` и `MANUAL-DOWNLOADS.csv`.
- `Install-Local.ps1` проверяет права администратора, читает `apps.json`, устанавливает только локально найденные EXE/MSI/PowerShell-файлы с заданными параметрами и пишет Transcript в `Logs`.
- `Install-PythonLibraries.ps1` предназначен для установки Python-библиотек из локальных wheel-файлов.
- `Invoke-NetworkDeploy.ps1` читает `computers.txt`, копирует текущую папку на `\PC\C$\ProgramData\ClassroomSoftwareDeploy` посредством Robocopy и запускает локальный скрипт через PsExec от LocalSystem.

В `apps.json` на момент проверки находится 41 запись. В числе известных записей есть браузеры, 7-Zip, VS Code, Python, PostgreSQL/pgAdmin, Docker Desktop, Arduino IDE, DBeaver, Git, GitHub Desktop, Adobe, Autodesk, графические и учебные приложения и другие позиции. Это текущий рабочий список, а не окончательный утверждённый каталог.

## 2.3. Известные ограничения текущего деплоера, которые необходимо учитывать

1. Подготовитель проходит по записям `apps.json` и пытается скачать записи с заполненными `DownloadUrl` и `Installer`; сейчас выбор на скачивание не отделён достаточно явно от `Enabled` (который используется установщиком). Нужно разделить `SelectedForPackage`/`DownloadEnabled` и `InstallEnabled` или эквивалентные явные флаги.
2. Существующая схема манифеста смешивает каталог ПО, свойства загрузки и команды установки. Их нужно постепенно разделить: каталог приложений, профиль пакета и описание конкретной версии payload.
3. Текущий установщик поддерживает простые типы MSI, EXE и PowerShell, но не имеет полноценной модели ZIP/portable, Visual Studio Layout, Adobe Managed Package, Autodesk deployment, Unity modules, драйверов и сложных зависимостей.
4. Для MSI параметры в `Install-Local.ps1` заданы фиксированно (`/qn /norestart`). Для некоторых MSI потребуются свойства/трансформации/специфические аргументы.
5. Для EXE необходимы непустые заранее проверенные аргументы; это правильное безопасное поведение, его нельзя заменять угадыванием ключей.
6. Проверка результата установки в основном опирается на exit code установщика. Необходимо добавить detection rules и, по возможности, последующую инвентаризацию.
7. PythonLibraries пропускается основным циклом и устанавливается отдельным скриптом из wheelhouse. Нужна интеграция с профилем пакета, совместимостью Python/архитектуры и явным вызовом.
8. ZIP/portable приложения сейчас не устанавливаются общим циклом.
9. LAN-скрипт копирует весь комплект на каждый компьютер последовательно; нет ограничения параллельности, нормальной сводки JSON, автоматического сбора удалённых журналов и результата инвентаризации.
10. Запуск PsExec от LocalSystem не подходит автоматически для каждого приложения: некоторые установки требуют пользовательского контекста, пользовательского профиля, входа/лицензии или интерактивного подтверждения. Контекст выполнения должен быть описываемым свойством установщика.
11. Подготовка USB может выполняться в каталоге Downloads, а не непосредственно на USB. Корень пакета должен задаваться пользователем/определяться явно и проверяться до скачивания.
12. Файл, который уже существует и имеет ненулевой размер, сейчас может быть принят как уже имеющийся до полной проверки происхождения/версии; нужно каждый раз проводить полную проверку, а при несовпадении предлагать повторную загрузку/карантин.
13. Скачивание HTML-страницы вместо бинарного установщика частично выявляется по размеру, но этого недостаточно. Нужны проверка ожидаемого типа, Content-Type (как подсказка, не единственный критерий), сигнатуры формата и/или цифровой подписи.
14. В текущем сетевом сценарии требуется PsExec, административная шара, соответствующие права и правила брандмауэра. Это нужно честно документировать и проверять до копирования.

**Не исправлять все эти пункты одной большой правкой.** Порядок реализации ниже специально разбит на мелкие коммиты.

# 3. Концепция и границы архитектуры

## 3.1. Модули

1. **Inventory** — сбор локальных сведений о ПО (ProgramScraper), экспорт JSON/XLSX, импорт отчётов нескольких ПК.
2. **Catalog** — нормализация, дедупликация, агрегирование найденных приложений и подготовка списка-кандидата для загрузки.
3. **Package Builder** — сопоставление приложения с официальным источником/пакетным адаптером, скачивание payload, ручное добавление, хэширование, проверка и сборка пакета выпуска.
4. **Deployment Engine** — проверка пакета и установка с локального USB/кэша; никаких сетевых загрузок с целевого ПК.
5. **LAN Manager** — доставка пакета от центрального ПК/сервера на выбранные Windows-ПК в локальной сети и запуск локального Deployment Engine.
6. **Verification & Reports** — повторная инвентаризация, сравнение фактического состояния с выбранным профилем, сводный отчёт.

## 3.2. Не делать в первой версии

- Не создавать сложный GUI/веб-панель. На первом этапе — PowerShell CLI/простое меню запуска и CSV/JSON/XLSX.
- Не писать собственный универсальный downloader для сайтов, требующих CAPTCHA, авторизацию или динамическую генерацию ссылок.
- Не автоматизировать обход лицензирования и активации.
- Не пытаться автоматически ставить любой найденный сканером продукт без проверки пользователем.
- Не устанавливать браузерные веб-сервисы как Windows-программы. Chrome/Firefox/Edge/Яндекс Браузер — допустимы, веб-сервисы типа Figma Web/Pixlr/Convertio — не являются установочными позициями, если нет отдельного официального desktop-клиента.
- Не включать драйверы, KB, системные Runtime и Windows Features в список пользовательских приложений по умолчанию. Они могут отображаться в расширенной инвентаризации, но должны иметь отдельную категорию и отдельное подтверждение.
- Не переносить реальные коммерческие установщики в репозиторий исходного кода.

## 3.3. Технологические рамки

- Windows 10/11 x64 — первая целевая платформа. Уточнять поддержку Windows 10 с учётом редакции и жизненного цикла; не отбрасывать её молча.
- Windows PowerShell 5.1 — минимальная совместимость на первом этапе.
- Использовать встроенные средства Windows/.NET по возможности.
- XLSX оставить на существующем Open XML/.NET механизме ProgramScraper.
- Runtime не должен требовать интернет, Chocolatey, WinGet, PowerShell Gallery или внешних модулей.
- Тестовая среда разработки может использовать Pester, но готовый USB-пакет не должен требовать Pester для установки.
- Все пути должны быть относительными от корня комплекта; не хардкодить букву USB-диска.

# 4. Пользовательские сценарии и требования

## 4.1. Сценарий A — первичная инвентаризация одного ПК

1. Пользователь запускает `Run.bat` или новый общий launcher.
2. ProgramScraper собирает данные.
3. Создаётся прежний Excel-отчёт и дополнительный JSON-файл.
4. В каталоге сохраняются компьютер, дата/время, ОС, архитектура, версия скрипта и источники данных.
5. Пользователь может импортировать этот отчёт в общий каталог.

Критерии:
- Старый XLSX создаётся с прежними листами и без необходимости Excel.
- JSON создаётся без зависимости от разбора текста XLSX.
- Ошибка одного источника (например, winget недоступен) не должна блокировать остальные источники.

## 4.2. Сценарий B — сбор результатов нескольких ПК

1. С каждого ПК получается JSON/XLSX инвентаризации.
2. JSON-отчёты импортируются в общий каталог.
3. Система объединяет совпадающие приложения, сохраняя исходные варианты написания и список компьютеров.
4. Пользователь фильтрует записи и утверждает, какие программы нужно подготовить к загрузке.

Дедупликация должна быть осторожной:
- первичный ключ сопоставления — нормализованное имя + издатель + архитектура/тип установки;
- при наличии надёжного идентификатора (winget ID, ProductCode MSI, PackageFamilyName и т.п.) он имеет больший приоритет;
- похожие имена от разных издателей автоматически не объединять;
- версии разных компьютеров сохранять как набор, а не затирать одной версией;
- пользователь должен иметь возможность объединить/разъединить записи вручную.

## 4.3. Сценарий C — каталог-кандидат и список загрузки

Система формирует перечень:

- название и издатель;
- обнаруженные версии и число компьютеров;
- область установки (пользователь/компьютер), архитектура;
- исходное имя и источник обнаружения;
- нормализованный ID приложения;
- статус сопоставления с записью каталога;
- предполагаемый официальный источник;
- способ получения payload;
- требование лицензии/аккаунта;
- состояние: `NeedsReview`, `ReadyToDownload`, `ManualDownload`, `NoSource`, `Excluded`.

Пользователь утверждает список. **Автоматический поиск источника не равен автоматическому разрешению скачивания.**

## 4.4. Сценарий D — подготовка пакета на ПК с интернетом

1. Пользователь создаёт профиль, например `Classroom-Design`, `Programming-Lab` или `Full-Classroom`.
2. Выбирает утверждённые приложения.
3. Для каждого элемента выбирает конкретную версию/канал, архитектуру, язык, source provider и настройки.
4. Package Builder получает payload на подготовительном ПК, сохраняет в папку выбранного пакета.
5. Все файлы проверяются: имя, размер, SHA-256, тип файла, Authenticode при наличии и expected publisher.
6. Формируется манифест пакета и отчёт готовности.
7. Пакет помечается `Ready` только если все обязательные payload и зависимости доступны и проверены.

Подготовительный ПК может иметь интернет; целевые ПК — нет.

## 4.5. Сценарий E — USB-установка

1. Пакет переносится на USB/внешний SSD.
2. Целевой компьютер запускает `INSTALL-FROM-USB.cmd`.
3. Деплоер определяет корень пакета от пути запуска, проверяет манифест и хэши.
4. Выполняет preflight (ОС, архитектура, свободное место, права, перезагрузка/занятый процесс, доступность payload).
5. Устанавливает выбранные приложения по порядку зависимостей.
6. Пишет локальные логи и machine-readable result.
7. При отсутствии файла, хэш-ошибке или неизвестных silent-параметрах безопасно пропускает приложение и сообщает причину.

На этом этапе целевой ПК не должен пытаться разрешать DNS или обращаться к интернету. Предусмотреть тест/режим, позволяющий доказать отсутствие HTTP-запросов на целевом ПК.

## 4.6. Сценарий F — развёртывание по локальной сети

1. Администратор указывает сетевой пакет и список ПК.
2. Менеджер проверяет разрешение имён, доступность SMB/admin share или выбранного транспорта, права, свободное место и возможность удалённого запуска.
3. Пакет доставляется на локальный диск каждого ПК (предпочтительный первоначальный вариант) либо читается с доверенной read-only SMB-папки.
4. На каждом ПК локальный движок запускается с одинаковым package manifest.
5. Управляющая машина получает итоговый статус и логи.
6. Ошибка одного ПК не останавливает обработку остальных.

Требования:
- ограничение параллелизма (настраиваемое, начально 3–5 ПК);
- retry для временных сетевых ошибок;
- таймаут на этап копирования/установки;
- уникальный DeploymentId;
- проверка версии пакета, хэша и свободного места;
- защита от одновременного запуска нескольких заданий на одном ПК;
- не сохранять пароль в `computers.txt`, JSON, логах или командной строке;
- поддержать текущий PsExec как первый transport adapter, но изолировать его за интерфейсом. PowerShell Remoting можно добавить отдельным адаптером позднее.

## 4.7. Сценарий G — проверка после установки

1. На целевых ПК запускается инвентаризация.
2. Формируется JSON-результат.
3. Он собирается на управляющей машине.
4. Система сравнивает фактическое ПО и версии с профилем/манифестом.
5. Формируется отчёт: `Installed`, `Missing`, `WrongVersion`, `Failed`, `NotVerified`, `Extra`.

Эта функция полезна, но должна идти после реализации основного пути «инвентаризация → каталог загрузки → offline package → deployment».

# 5. Данные и форматы

## 5.1. Принцип разделения сущностей

Не хранить всё в одном `apps.json`. В конечной модели различать:

1. **InventoryRecord** — что было обнаружено на конкретном ПК.
2. **SoftwareCatalogEntry** — нормализованная карточка программы.
3. **PackageProfile** — набор выбранных пользователем программ для класса/задачи.
4. **PackageArtifact** — конкретный установочный файл (версия, архитектура, URL/источник, SHA-256, подпись).
5. **InstallRecipe** — проверенная команда установки, detection rules, exit codes, контекст и reboot policy.
6. **DeploymentJob** — развёртывание конкретного выпуска на набор ПК.
7. **InventoryReport** — фактическое состояние ПК после установки.

## 5.2. Inventory JSON — минимальная схема

```json
{
  "schemaVersion": "1.0",
  "scanId": "GUID",
  "computer": {
    "name": "PC-01",
    "osCaption": "Microsoft Windows 11 Pro",
    "osVersion": "10.0.x",
    "architecture": "x64"
  },
  "scan": {
    "startedAtUtc": "2026-01-01T10:00:00Z",
    "completedAtUtc": "2026-01-01T10:00:15Z",
    "tool": "ProgramScraper",
    "toolVersion": "...",
    "sources": ["HKLM-Uninstall-x64", "HKLM-Uninstall-x86", "User-Uninstall", "Winget"]
  },
  "applications": [
    {
      "displayName": "Example App",
      "publisher": "Example Publisher",
      "displayVersion": "1.2.3",
      "architecture": "x64",
      "scope": "Machine",
      "installLocation": "C:\\Program Files\\Example",
      "uninstallString": "...",
      "quietUninstallString": "...",
      "source": "Registry-HKLM-x64",
      "registryKey": "...",
      "userName": null,
      "wingetId": null,
      "productCode": null,
      "categoryHint": "Application"
    }
  ],
  "warnings": []
}
```

Схема примерная. Поля реального исходного скрипта нужно сопоставить аккуратно. Отсутствующие данные хранить как `null`, а не выдумывать. JSON должен иметь `schemaVersion` и быть независимым от локали PowerShell.

## 5.3. Каталог ПО

Для нормализованной карточки предусмотреть:

- `id` — стабильный собственный slug/UUID;
- `displayName`, `publisher`;
- `aliases` — альтернативные имена;
- `category` (Development, Graphics, 3D, Education, Utility, Browser, Runtime, Driver, WindowsComponent, Update, Other);
- `isDesktopInstallable`;
- `licenseType` (Free, OpenSource, Freemium, Commercial, Educational, Unknown);
- `officialWebsite`, `downloadPage`;
- `sourceProvider` и `providerPackageId`;
- `supportedOS`, `architectures`;
- `reviewStatus` и `notes`.

Категория и тип лицензии не должны автоматически выводиться только из названия. Неизвестное помечать `Unknown`/`NeedsReview`.

## 5.4. Package manifest — минимальные поля

Для выпуска пакета предусмотреть:

- `schemaVersion`, `packageId`, `packageName`, `packageVersion`, `createdAtUtc`, `createdBy`, `targetOS`, `architecture`;
- список `applications`;
- для приложения: `id`, `version`, `installerType`, `relativePath`, `sizeBytes`, `sha256`, `publisher`, `downloadSource`, `licenseType`, `selected`, `required`, `dependencies`;
- `installRecipe`: точные `arguments`, `workingDirectory`, `executionContext` (`System`, `ElevatedUser`, `CurrentUser`, `Interactive`), `successExitCodes`, `rebootExitCodes`, `timeoutSeconds`, `detectionRules`;
- `prerequisites`;
- `payloadFiles` с хэшами;
- `validationStatus`.

Не хранить секреты, токены, логины, пароли и персональные данные в манифесте.

## 5.5. Типы установочных payload

Поддержать поэтапно:

1. MSI — базовая поддержка и пользовательские MSI properties.
2. EXE — только если recipe с точными подтверждёнными аргументами.
3. ZIP/portable — только после определения безопасного типа действия: распаковка в целевую папку, копирование ярлыка/конфигурации (не считать произвольный ZIP установщиком).
4. PowerShell recipe — только доверенный скрипт внутри пакета, проверенный хэш, allowlist/подтверждение; не исполнять произвольный код из каталога.
5. Специализированные layouts/managed packages (Visual Studio, Adobe, Autodesk и т.п.) — отдельные интеграционные типы, когда есть тесты и официально поддержанный офлайн-механизм.

# 6. Источники получения установщиков

## 6.1. Абстракция провайдера

Package Builder должен поддерживать поставщиков/способы получения payload как отдельные адаптеры:

- `DirectUrlProvider` — официальный прямой URL;
- `ManualProvider` — файл скачивает и кладёт пользователь;
- `WingetProvider` — только получение метаданных/загрузка реального payload, если это технически и лицензионно возможно; проверять зависимости и условия источника;
- `ChocolateyProvider` — пакет Chocolatey может быть метаданными/рецептом, но `.nupkg` не считать достаточным офлайн payload;
- специализированные провайдеры позже.

Провайдер не должен отвечать за установку. Он только получает/регистрирует конкретные файлы и метаданные.

## 6.2. Chocolatey — чёткое правило

`choco install` на целевом ПК без интернета не решает задачу. Нельзя просто положить `.nupkg` на USB и объявить это готовым автономным приложением: пакет часто скачивает EXE/MSI с внешнего сайта при установке.

Для offline-ready артефакта нужно иметь payload, зависимости и их точные версии/хэши. Если получение payload требует лицензированного Chocolatey Package Internalizer, это указать как опциональный коммерческий путь; базовая система не должна требовать платный Chocolatey.

## 6.3. Проверка источников и безопасности

- Предпочитать официальные сайты производителей и официальные репозитории.
- Сохранять исходный URL, дату/время скачивания, HTTP status, filename, размер, SHA-256 и цифровую подпись (если Authenticode применим).
- `SHA-256`, рассчитанный после скачивания, фиксирует целостность относительно подготовленного пакета, но сам по себе не доказывает подлинность файла. Для доверия использовать HTTPS от официального источника и проверку подписи/ожидаемого издателя, если доступно.
- Не обходить авторизацию, CAPTCHA, региональные и лицензионные ограничения.
- Если невозможно автоматизировать загрузку надёжно, создать запись Manual с точной папкой назначения и инструкцией.
- Если в каталоге найдено приложение, не добавлять его источник автоматически без проверки человеком.

# 7. Интерфейс и команды первой версии

В первой версии достаточно общего `.cmd`-launcher с текстовым меню. GUI не является условием завершения MVP.

Предлагаемые действия:

```text
1. Сканировать этот компьютер
2. Импортировать JSON/XLSX отчёты инвентаризации
3. Просмотреть/экспортировать каталог найденных программ
4. Создать/изменить профиль пакета
5. Подготовить офлайн-пакет (компьютер с интернетом)
6. Проверить готовность пакета и файлы
7. Установить пакет с USB на этом ПК
8. Развернуть пакет по локальной сети
9. Собрать отчёты с целевых ПК
10. Сравнить план и фактическое ПО
0. Выход
```

Реализовывать меню только после появления стабильных отдельных команд/функций. CLI-параметры предпочтительнее для автоматизации и тестов.

Все скрипты должны поддерживать `-WhatIf`/dry-run там, где действие изменяет систему или удалённый ПК. Dry-run не должен скачивать, устанавливать или изменять файлы, кроме явно указанных тестовых временных директорий.

# 8. Подробный план реализации небольшими коммитами

План состоит из независимых маленьких задач. Агент должен выполнять их строго по порядку, но может предложить перестановку только с объяснением и согласованием. Названия коммитов примерные.

## Этап 0. Базирование и защита существующего поведения

### Коммит 01 — `docs: add integration baseline`
- Добавить этот документ в `docs/` или корень репозитория.
- Добавить `docs/BASELINE.md` с реальными путями, версиями и SHA исходных файлов/архивов.
- Не менять runtime-код.
- Проверка: документация ссылается только на файлы, действительно существующие в репозитории.

### Коммит 02 — `test: add PowerShell syntax smoke checks`
- Добавить минимальный тест/скрипт, который проверяет синтаксис всех `.ps1`.
- Не выполнять сами скрипты и не скачивать ПО.
- Проверка: синтаксические ошибки возвращают ненулевой exit code.

### Коммит 03 — `test: add fixture inventory and package manifests`
- Создать маленькие тестовые JSON/CSV fixtures без реальных установщиков.
- Добавить тестовые данные для двух ПК, одинаковой программы с разными версиями, одноимённых продуктов разных издателей, Windows component и runtime.

### Коммит 04 — `refactor: centralize project root resolution`
- Ввести одну функцию определения корня проекта и относительных путей.
- Существующие `.cmd`-точки входа должны продолжить работать из папки с пробелами и с разных букв диска.
- Проверка: запуск `-WhatIf` из временной папки с пробелами.

## Этап 1. Расширить ProgramScraper без поломки XLSX

### Коммит 05 — `feat(inventory): add schema version and scan metadata model`

### Коммит 06 — `feat(inventory): export machine-readable JSON`

- Проверка: сериализация/десериализация sample JSON, кириллица, null, спецсимволы.

### Коммит 07 — `feat(inventory): expose application records separately from system records`
- Сформировать отдельную коллекцию приложений, предназначенную для каталога загрузки.

### Коммит 09 — `feat(catalog): import one inventory JSON`

### Коммит 10 — `feat(catalog): aggregate inventories from multiple computers`
- Импорт нескольких JSON.
- Агрегировать occurrences, список ПК, установленные версии, publishers, architecture/scope.

- Проверка: два sample ПК с общей программой формируют один агрегат с двумя компьютерами.

### Коммит 11 — `feat(catalog): add conservative duplicate matching`
- Добавить нормализацию пробелов/регистра/типовых суффиксов в отдельную функцию.

- Проверка: продукты с одинаковым displayName и разным publisher остаются разными.

### Коммит 12 — `feat(catalog): export reviewable software candidate list`
- Экспортировать CSV/JSON со статусами `NeedsReview`, `ReadyToDownload`, `ManualDownload`, `NoSource`, `Excluded`.
- Добавить поля частоты обнаружения и источника.

- Перенести поэтапно `DownloadUrl`, installer metadata и install arguments в отдельные сущности.

## Этап 3. Package Builder и автономный payload

### Коммит 17 — `feat(builder): add DirectUrl provider`
- Создать отдельную функцию/модуль скачивания прямого URL.
- Записывать в `.partial`, после успешной проверки атомарно перемещать в итоговый файл.
- Поддержать таймаут, retry, отмену и понятный статус.

### Коммит 18 — `feat(builder): add manual payload registration`
- Добавить flow: пользователь кладёт файл в ожидаемую папку и подтверждает регистрацию.
- Система вычисляет размер и SHA-256, просит/сохраняет source URL, дату и заметку.

### Коммит 19 — `feat(builder): verify payload file type and signature`
- Добавить проверку расширения/сигнатуры формата и Authenticode, когда применимо.

### Коммит 22 — `feat(builder): add package report and offline media export`
- Подготовить отчёт `PACKAGE-REPORT.html/csv` (минимум CSV/Markdown допустим) с именами, версиями, размером, хэшами и действиями.
- Копировать/экспортировать готовый пакет на выбранный USB/SSD.
- Проверка: экспортированный каталог открывается на другом диске и проходит verify.

# 9. Требования к качеству и тестированию

## 9.1. Минимальные проверки каждого коммита

- Парсинг PowerShell 5.1 (AST parser / `Parser::ParseFile`).
- Pester tests или эквивалентные unit tests для новой логики.
- Проверка, что существующие `Run.bat`, `PREPARE-USB.cmd`, `INSTALL-FROM-USB.cmd` не были случайно сломаны.
- Проверка путей с пробелами, кириллицей и разными буквами диска.
- Ни один unit test не должен требовать интернета или административных прав.

## 9.2. Полный сценарий приёмки

1. На подготовительном Windows 10/11 x64 ПК с интернетом собрать inventory с 2–3 тестовых машин (можно начать с fixtures).
2. Получить общий application candidate catalog.
3. Исключить Windows components, drivers, KB, runtimes и веб-сервисы; оставить подтверждённые desktop-приложения, включая браузеры.
4. Утвердить профиль из минимум трёх тестовых программ разных типов: MSI, EXE с явными silent args, portable ZIP.
5. Скачать/зарегистрировать payload и создать пакет. Все payload имеют SHA-256, источник и дату.
6. Проверить пакет (Ready) и экспортировать на USB/SSD.
7. Отключить интернет на тестовой Windows VM/ПК.
8. Установить пакет с USB. Проверить, что процесс не делает HTTP/HTTPS запросов и не вызывает choco/winget для загрузки.
9. На другой тестовой VM развернуть тот же пакет по LAN из управляющей машины. У целевой VM нет интернета.
10. Проверить логи, exit codes, копирование и повторный запуск.
11. Запустить post-deploy inventory и получить сводный отчёт.
12. Проверить отрицательные сценарии: отсутствующий payload, неверный SHA, отсутствующая зависимость, неизвестные EXE args, отказ доступа к одному ПК, обрыв сети при копировании.

## 9.3. Definition of Done для MVP

MVP можно считать готовым, когда работает весь основной поток:

**инвентаризация → агрегированный список ПО → ручное утверждение → подготовка реальных автономных payload → package manifest/verify → USB offline install → LAN copy + offline install.**

Пост-развёртывательная проверка должна быть реализована минимум на уровне JSON-инвентаризации и сравнения с профилем, но сложные GUI и расширенная аналитика могут остаться после MVP.

# 10. Безопасность, лицензии и операционные требования

- Использовать только официальные источники/проверяемые источники и соблюдать лицензии ПО.
- Не хранить учётные данные в конфигурации или логах.
- Не принимать произвольные install arguments из неподписанного каталога без review.
- Проверять SHA-256 всех файлов перед запуском.
- По возможности проверять Authenticode signature и Publisher.
- Не запускать скрипты из payload до проверки хэша и статуса доверия.
- Логи не должны содержать пароли, токены и чувствительные пользовательские данные.
- В манифесте и отчётах не собирать персональные данные, не необходимые для учёта программ.
- Подготовить режим `-WhatIf` для любых удалённых/установочных операций.
- Сначала тестировать на одной изолированной машине, затем на 2–3 ПК, и только потом на 20–30 ПК.
- Предусмотреть возврат/откат только там, где конкретный установщик официально поддерживает uninstall/rollback; не обещать универсальный rollback.

# 12. Инструкция по ведению коммитов

## 12.1. Формат коммита

Использовать понятные conventional commit prefixes:

- `docs:` — документация;
- `test:` — тесты/фикстуры;
- `feat:` — небольшая новая возможность;
- `fix:` — исправление ошибки;
- `refactor:` — внутренний рефакторинг без изменения поведения;
- `chore:` — техническая настройка.

Пример:

```text
feat(inventory): export scan result as JSON
```

## 12.2. Размер коммита

- Один коммит должен решать одну задачу и быть понятен при отдельном просмотре.
- Желательно 1–3 логически связанные файла; исключение — генерация схемы/тестов для одной функции.
- Если изменение начинает затрагивать разные модули, разделить его.
- Не делать коммиты вида `update all`, `fix everything`, `integrate projects`.
- Не удалять старое поведение до появления тестов и рабочего replacement.

## 12.3. Отчёт агента после каждого шага

После каждого коммита выводить:

```text
Commit: <hash> <message>
Что изменено: ...
Проверки: ...
Результат: PASS / FAIL
Известные ограничения: ...
Следующий пункт: ...
```

Если тест не может быть запущен (например, отсутствует Windows VM), отметить это как `NOT RUN`, а не утверждать, что он прошёл.

## 12.4. Не выполнять без разрешения пользователя

- реальное скачивание десятков/сотен гигабайт ПО;
- установку приложений на рабочий компьютер;
- удалённый запуск на всех ПК;
- удаление старых версий ПО;
- перезагрузку;
- изменение доменных политик, Firewall, SMB, UAC или системных настроек;
- загрузку лицензированных установщиков в публичный репозиторий.

# 13. Рекомендуемый первый запуск агентной работы

До первого изменения кода агент должен:

1. Клонировать `https://github.com/circumF1ex/programscraper` и создать отдельную рабочую ветку.
2. Получить от пользователя актуальный архив/репозиторий `ClassroomSoftwareDeploy-OfflineUSB` и распаковать его в отдельную папку для анализа. Не смешивать две исходные копии до сравнения.
3. Составить `docs/BASELINE.md`: список файлов, хэши, команды запуска, доступные параметры и известные проблемы.
4. Запустить только безопасные статические проверки. Не запускать подготовку USB и установку ПО без разрешения.
5. Предложить минимальную стратегию слияния: сохранить ProgramScraper как модуль Inventory, деплоер как Deployment/Builder, сначала ввести общий JSON-контракт.
6. Выполнить только коммиты 01–04, показать результат пользователю и продолжить после проверки.

**Не начинать с переноса всех файлов и переписывания launcher.** Первый реальный интеграционный контракт — JSON-инвентаризация. После его стабилизации можно строить каталог программ.
